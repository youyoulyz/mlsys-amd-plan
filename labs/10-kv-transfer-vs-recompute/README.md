# 10 · 4 GB 对话记忆：从内存搬回 GPU 还是让 GPU 重新算？慢盘上搬反而更慢

> **一句话在做什么**：一个 32B 模型聊了 3.2 万字，它的对话记忆（KV cache）约 4 GB。现在要恢复这段对话，两条路：把 4 GB 从慢速存储搬回 GPU，或让 GPU 把这 3.2 万字重新算一遍。写个小计算器代入实测带宽：走内存（PCIe，~27 GB/s）搬只要 150 ms，走 SSD（~4 GB/s）搬要 2.1 s——**比 GPU 重算（~0.9–1.5 s）还慢**。该搬还是该重算，取决于盘在哪个速度档。

## 实验导读

显存装不下对话记忆时的标准做法是分层：GPU → 内存 → SSD，按需换入。直觉是"算一次很贵，存下来下次直接加载肯定赚"。这个实验给出一个能代入你自己机器数字的计算器：什么时候"搬"赢，什么时候"重算"赢。

跑完（或读完）你会知道：

- 为什么"搬一定比重算省"在慢速盘上是错的：GPU 算力在变快、总线/盘速相对变慢（"计算-传输倒挂"），且搬运期间 GPU 完全空等（实测可占推理总耗时 72.3%）；
- 决策边界公式：搬的代价 = 字节数 ÷ 带宽 + 启动开销，重算的代价 = token 数 × 每 token 重算时间，两边一比就知道该走哪条路；
- "倒挂阈值"：前缀多短时重算开始划算——盘越慢、GPU 越强，阈值越往短了挪；
- 怎么把它套到你自己的机器：实测你的 PCIe/SSD 有效带宽和 prefill 吞吐，代入脚本 3 行命令出结论。

| 参数 | 人话解释 | 本实验默认值 |
| --- | --- | --- |
| 4 GB KV | 3.2 万字 × 128 KB/字 | 32K tokens |
| PCIe ~27 GB/s | CPU 内存 → GPU 的搬速 | 25–30 GB/s 中值 |
| SSD 2–6.8 GB/s | 盘 → GPU 的搬速（区间敏感） | 4.4 GB/s 中值 |
| 27k 字/秒 | GPU 重新"读"前缀的速度（prefill） | 20k–35k 中值 |

## 你会怎么猜

分层存储（GPU HBM → CPU DRAM → NVMe）+ LRU 换入换出，是避免重复 prefill 的标准做法。你的直觉：

- "KV 算一次很贵，存下来下次直接加载，省了就是赚了。"
- 所以：能搬就搬，别浪费算力重算。

## 实测会看到（文献实测 + 可代入公式）

以一个 32B、GQA、FP8、32K 上下文的典型模型为例，KV 物理尺寸约：

```
S_KV = 32,000 × 128 KB ≈ 4 GB
```

把 4 GB 从慢速介质搬回 GPU 的代价：

| 介质 | 实测有效带宽 | 单向搬运 4 GB | 代价 |
| --- | --- | --- | --- |
| NVMe SSD | 2–6.8 GB/s | **0.6–2.0 s** | 搬运期间 GPU 张量核空等；**SSD 卸载时 GPU 空转气泡可占总耗时 72.3%** |
| PCIe 4.0（主机内存） | 25–30 GB/s | **130–160 ms** | 仍非免费 |

而**重算**（现代卡处理长前缀 FP8 prefill 通常 20k–35k tokens/s）：

| 方式 | 耗时 |
| --- | --- |
| 全量重算 32K 前缀 | **~0.9–1.5 s** |
| 只重算增量/变动部分 | **数十 ms** |

**反直觉**：走 PCIe 搬 4 GB 要 130–160 ms，比 GPU 重算的 0.9–1.5 s 快得多——该搬。但走 NVMe 要 0.6–2.0 s：**慢端（2 GB/s）比重算还慢**，快端（6.8 GB/s）又开始划算——结论对盘速区间敏感，且搬运期间 GPU 完全空等（气泡可占 72.3%）。"搬运一定比重算省"在慢速介质上是**错的**。

还有一个被忽视的浪费源：**"僵尸 KV"**——生产环境 31%–36% 的显存被已终止、不可复用的中间状态占据（KVTether），LRU 的时间局部性盲区会把瞬态思维链误判为热数据死锁在显存里。

**决策边界（只有满足它，换入才有正收益）：**

```
N_c · μ / B_H2D + τ_load  <  N_c · t_pf
（搬运字节 / 带宽 + 启动开销  <  重算耗时）
```

其中 `N_c` = 缺失前缀 token 数，`μ` = 每 token KV 字节，`B_H2D` = 主机→设备有效带宽，`τ_load` = 启动固定开销，`t_pf` = 当前硬件对应前缀长度下的每 token prefill 耗时。

**一句话结论**："搬运 vs 重算"是**运行时动态决策**，不是"存下来就行"。介质越慢、前缀越长、GPU 越强，重算越可能赢——调度器必须实时采样总线带宽与 prefill 吞吐来仲裁，总线一堵就该触发"原位分块重算"而不是发 I/O。

## 为什么会这样

GPU prefill 算力的增速 > 存储/总线 I/O 带宽的增速（"计算-传输倒挂"）。搬运是**串行阻塞**（GPU 空等 I/O），重算是**并行利用算力**。当搬运延迟 ≥ 重算延迟时，搬运不仅不省，还把 GPU 的计算单元晾着。这就是为什么分层缓存系统普遍缺一个在调度层面对"倒挂"的运行时仲裁。

## 用了什么工具，为什么

- **为什么写一个计算器而不是直接跑实验**：这个决策是"运行时"的——每次换入都要现场比较"搬 vs 重算"，而两边数字（盘速、prefill 吞吐）随硬件和负载变。一个 30 行、可代入你自己实测数字的计算器，比一份固定环境的实验更能回答问题；本 lab 自带的默认值就来自已发表的实测（来源见下）。
- **prefill 是什么**：模型"读"你输入的前缀、为后续生成做准备的过程（区别于逐字生成的 decode）。"重算"省的就是这笔 prefill 的钱。
- **为什么本 lab 标"实测数据待跑"**：默认数字来自文献/评测，不是本机实测。在自己的机器上测 PCIe/NVMe 有效带宽 + 对应前缀的 prefill 吞吐后代入，才是第 3–4 周该交的作业（lab 11 测的正是"盘那一层"的真实写速）。
